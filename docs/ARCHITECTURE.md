# 架构说明

## 一、分层与数据流向

```
                 ┌──────────────────────────────────────┐
   页面层         │  pages/*.vue                          │
                 │  只做:展示、交互、调 api              │
                 │  不做:业务规则、拼 URL、处理 code      │
                 └───────────────┬──────────────────────┘
                                 │ ① await memberApi.getList(...)
                 ┌───────────────▼──────────────────────┐
   接口声明层     │  api/*.ts                             │
                 │  只描述「有哪些接口、参数、返回类型」   │
                 │  不知道底下是 mock 还是真后端          │
                 └───────────────┬──────────────────────┘
                                 │ ② request<T>({url, data})
                 ┌───────────────▼──────────────────────┐
   网络层         │  utils/request.ts   ← 全项目唯一出口  │
                 │  VITE_USE_MOCK 分流在这里发生          │
                 │  统一拆 Result 壳、注入 token、toast   │
                 └──────┬──────────────────────┬────────┘
              mock=true │                      │ mock=false
        ┌───────────────▼──────┐      ┌────────▼────────────┐
        │ mock/index.ts        │      │ uni.request → tsa-api│
        │ 方法+路径匹配、延迟、 │      │ 返回同样的 Result 壳 │
        │ 404、切片分页        │      └─────────────────────┘
        └───────────────┬──────┘
                        │ 读
                ┌───────▼──────────┐
                │ mock/data/*.json │  ← 可整目录删除,业务代码不受影响
                └──────────────────┘
```

组件层 `components/` 被页面横向调用;`stores/` 被页面与组件横向调用;
`types/`、`constants/` 谁都能引,它们不引任何人。

**依赖方向永远单向**:pages → components/stores/api → utils → types/constants。
出现反向引用(比如 `utils/request.ts` import 了某个页面)就是设计错了。

## 二、各目录职责与约束

| 目录               | 允许                                  | 禁止                                                         |
| ------------------ | ------------------------------------- | ------------------------------------------------------------ |
| `pages/`           | 取数、渲染、跳转、局部 UI 状态        | 直接 `uni.request`;写可复用业务规则;把页面私有状态塞进 store |
| `components/`      | 纯展示 + 事件上抛;**包装 TDesign**    | 自己发请求(数据一律由 props 传入);直接放过深的业务判断       |
| `api/`             | 声明接口与类型                        | 写 `if/else` 业务逻辑;出现 URL 拼接细节                      |
| `utils/request.ts` | 网络、鉴权头、统一错误处理、mock 分流 | 出现任何业务字段名                                           |
| `mock/`            | 模拟 HTTP 语义                        | 被 `pages/` 直接 import(只能由 request.ts 动态引入)          |
| `stores/`          | 跨页面共享状态                        | 当全局变量垃圾桶(判据见第四节)                               |
| `types/`           | 契约的单一事实来源                    | 放运行时代码(所以是 `.d.ts`)                                 |
| `constants/`       | 字典、枚举、主题色                    | 放只被一个页面用的常量(那该留在页面里)                       |
| `styles/`          | 主题 token 覆盖、通用工具类           | 放页面私有样式                                               |

### 关于 `types/` 为什么用 `.d.ts`

契约应当只有类型、没有实现。用 `.d.ts` 可以从物理上防止有人往里塞函数 ——
那会让它悄悄变成第二个 `utils/`。

## 三、组件包装层(TDesign 隔离)

本项目的核心约定:**页面不直接裸用 TDesign 的基础组件做业务 UI**,
业务级 UI 一律经 `components/Tsa*` 包一层。

原因很实际:`@tdesign/uniapp` 是 **0.10.x,未发 1.0**,7 个月发了 13 版,
破坏性变更的概率不低。包一层之后,升级时只改 `components/`,
而不是在十几个页面里全文搜索替换。

```
components/
├── TsaMemberCard/   乡贤列表项   内部用 t-avatar + t-tag
└── TsaFilterBar/    筛选面板     内部用 t-input + t-tag + t-button
```

**注意边界**:`t-button`、`t-tag` 这类纯原子控件**不需要**包装 ——
它们的行为就是设计系统本身,包一层只会增加噪音。
要包的是**有业务含义的组合**(一张乡贤卡片、一个筛选面板)。

## 四、什么状态该进 Pinia(判断标准)

这是本项目最值得单独讲的一节,因为**滥用状态管理是新手最普遍的过度设计**。

判据只有一个问题:

> **这份状态是否被两个及以上页面读取,且必须保持一致?**

- 是 → 进 store;
- 否 → 留在组件里的 `ref`。

本项目现在只有两个 store,都是这一条的正面案例:

| Store          | 为什么该进                                                                                                                                          |
| -------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| `memberFilter` | **地图页和乡贤列表页共用同一份筛选**。在地图上筛「深圳/互联网」,切到底部乡贤 tab 应该是同一批人。这是真实的跨页一致性需求,不是「为了用 Pinia 而用」 |
| `user`         | 登录态与资料被「我的」、详情页权限判断、请求头注入多处读取                                                                                          |

反面清单(**不要**进 store):

- 弹窗开合(`showFilter`)—— 单页面临时状态;
- 当前选中的某个成员(`selected`)—— 只有地图页关心;
- 表单草稿(`draft`)—— 见下一小节;
- 列表滚动位置、骨架屏开关。

`src/pages/member/list.vue` 里就有正例对照:列表数据 `list` 是页面私有的,
留在 `ref`;而筛选条件在 store。**页面私有的数据不要往 store 塞。**

### 草稿模式(draft pattern)

`TsaFilterBar` 里改的是本地 `reactive` 的 `draft`,点「确定」才写回 store。

理由:用户划拉一半反悔直接关掉,不应该污染地图上正在显示的结果。
这也是「表单状态该不该进 Pinia」的标准答案 —— **不该;只有确认后的结果才进。**

## 五、mock 与后端的对称性

mock 层刻意模拟真实 HTTP 语义,而不是「直接返回一个对象」:

| 对称点          | mock 做法                            | 为什么必须这样                                      |
| --------------- | ------------------------------------ | --------------------------------------------------- |
| 方法 + 路径匹配 | key 是 `"GET /members"` 这种形式     | 后端换 HTTP 语义时,前端会同样错                     |
| 统一响应壳      | 一律返回 `{code, message, data}`     | 否则页面要为 mock 和真接口写两套拆包逻辑            |
| 网络延迟        | 200~500ms                            | 不加延迟,loading 态永远不会被看到,学生练不到        |
| 未实现接口      | 返回 `code:404` + `console.warn`     | 静默返回 `undefined` 会让人查半天「数据怎么是空的」 |
| 字段投影        | `toMapPoint` / `toListItem` 显式列举 | 详情字段不会顺着列表接口漏出去                      |

### 显式列举 vs 解构丢弃

投影函数写成一个个字段 `return { id, name, ... }`,
而不是 `const {password, ...rest} = m; return rest`。

后者在字段增删时会**悄悄多传或不传**,而且解构出的未用变量会触发 lint。
显式列举会在契约变化时立刻暴露 —— 对教学项目,「错得明显」比「错得安静」好。

## 六、隐私与权限:前端隐藏 ≠ 数据没下发

`MemberDetail.contactVisible` 控制详情页是否渲染微信号与手机号。

但**必须在后端做权限过滤**:mock 阶段直接把 `phone` 塞进了 JSON,
这只是模拟数据无害;真接口如果照样把未公开成员的 `phone` 返回给前端,
那么抓包就能看到 —— 前端那个 `v-if` 拦不住任何人。

这条写进 `docs/API.md` 的「隐私」一节,后端实现时必须落实。

## 七、任务分层(给老师分配用)

分层架构的直接好处是**任务天然分级**,不同水平的学生不会互相阻塞:

| 级别 | 典型任务                                             | 会碰到哪几层                                    |
| ---- | ---------------------------------------------------- | ----------------------------------------------- |
| L1   | 改主题色、加一个行业选项、调首页文案                 | `styles/` 或 `constants/`,单文件                |
| L2   | 新增「乡会荣誉墙」列表:类型 + api + mock 路由 + 页面 | 四层各动一点                                    |
| L3   | 地图页当前视野成员计数、按区域着色                   | pages + utils + mock,要懂 `regionchange`        |
| L4   | 给 request 层加请求缓存与重复请求合并                | 只动 `utils/request.ts`,要懂 Promise 与生命周期 |
| L5   | 把 mock 换成真后端联调并修所有契约偏差               | 全链路,需要与后端组协同                         |

详细任务清单与验收标准见 [TASKS.md](TASKS.md)。
